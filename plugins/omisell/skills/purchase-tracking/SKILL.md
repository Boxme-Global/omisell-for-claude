# Omisell: purchase tracking

Goal: show which supplier purchase orders need a chase (late), a check (partly received) or nothing yet, so stock planning counts only goods that are really coming.

## Steps

1. **Open purchase orders.** `list_purchase_orders` with `state="open"` (the default: every purchase order not cancelled and not completed, of any age, because goods in transit are often old orders), `limit=50`. It returns `counts` per status (`status`, `label`, `count`) and `rows`: `purchase_code`, `reference_code`, `label`, `vendor_name`, `pickup_name`, `amount`, `currency`, `quantity_ordered`, `quantity_received`, `expected_delivery_date`, `created_time`, `overdue`.
   - One warehouse → add `pickup_address_ids` (from `list_pickup_addresses` with `keyword`).
   - One SKU, PO code or reference → add `keyword`.
   - One status → add `status` (codes come from `counts`; open orders never carry the cancelled or completed codes).
2. **History** ("what did we order last month?"): `state="all"` with `date_from` / `date_to` (created date, at most 90 days).
3. Refused with `missing_permission` → "Viewing purchase orders needs the purchase-order permission in Omisell. Ask the shop owner to grant it." Nothing else on this connection replaces it.

## Grouping the rows

- **Late**: `overdue` is true. The tool sets it only for orders whose goods have not reached the warehouse (new, approved, in transit) and whose expected date has passed. Days late = today − expected date.
- **Partly received**: `quantity_received` > 0 and below `quantity_ordered`. Show the missing units.
- **At the warehouse, not finished**: received or being inspected at the warehouse with nothing missing; someone still has to complete the order in Omisell.
- **On the way**: the rest. An order with no expected date cannot be late; say "no expected date" so the user can add one.
- Quantities are totals per purchase order, not per SKU. For a per-SKU answer search with `keyword` = that SKU, and say the quantities may include other SKUs on the same order.
- If `rows` holds fewer orders than `counts` adds up to, the late and partly received figures cover only the rows shown: say "among the 50 shown", say how many more there are, and offer a filter by status or warehouse. Only the per-status counts are totals.

## Answer

- Summary: N open purchase orders (from `counts`), how many late, how many partly received ("among the 50 shown" when cut off); "as of <dd/mm/yyyy hh:mm>".
- Table 1, late (most days late first): PO code · vendor · warehouse · expected date · days late · ordered / received · status.
- Table 2, partly received: PO code · vendor · ordered · received · missing.
- One line with the count per status label.
- Next: chase the vendor of the late orders, complete or reconcile partly received orders on the Omisell Purchase orders screen, re-check what runs out before the late goods arrive (`/omisell:stockout-forecast`), plan more if needed (`/omisell:reorder-plan`).

## Do not

- Do not use the returned-goods receiving report for purchase orders: it counts customer returns coming back, not supplier deliveries.
- Do not filter open orders by created date; old in-transit orders would disappear.
- Do not state paid or unpaid amounts; the tool does not return them (point to the Purchase orders screen).
