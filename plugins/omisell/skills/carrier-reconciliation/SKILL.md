# Omisell: carrier reconciliation

Goal: the accountant knows how much COD the carriers still owe, which parcels were paid a different amount, and which reconciliation statements are waiting on someone.

## Steps

1. **Period.** Unix seconds in the business time zone. `cod_reconciliation_status` accepts **at most 31 days**; `cost_statement_summary` at most 90 days.
2. **COD.** Call `cod_reconciliation_status` with `date_from`, `date_to`, `limit` 10 (max 20) and `date_field`:
   - `"delivered"` when the user asks about parcels delivered in the period ("COD giao tuần này"),
   - `"created"` (default) otherwise.
   Set `courier_ids` only when you already hold the carrier's id from another Omisell result; otherwise do not filter.
   It returns three tabs, each with `shipments`, `cod_amount`, `received`: `to_release` (awaiting reconciliation), `released` (reconciled), `abnormal` (amount differs), plus `abnormal_samples` (tracking code, COD, received, difference = received minus COD) and a `note`.
3. **Statements (only if asked, or the user says "bảng kê").** Call `cost_statement_summary` with `date_from`, `date_to` (statement creation date) and `statement_kind` `"purchase"` (default) or `"return"`; add `pickup_address_id` only when the user names one warehouse (`list_pickup_addresses`). It returns, per status (`label`: waiting verification, waiting approval, awaiting payment, paid), the number of statements, goods lines and amount. Per its `note`, the amount is the statements' cost of goods including VAT, and duplicate statements can exist when a schedule re-ran.
4. **Refused.** `missing_permission` on step 2 → "This needs the COD reconciliation permission in Omisell." On step 3 → "This needs the reconciliation statement permission." Run whichever part is allowed.

## Answer

- Summary: COD still awaiting reconciliation (amount + parcels), COD reconciled, number of abnormal parcels with their COD and received totals, with the period and which date it filters on ("parcels delivered 01/11-06/11/2026").
- Table 1: the three COD tabs - parcels, COD, received.
- Table 2: top abnormal parcels - tracking code, COD, received, "received minus COD". The abnormal tab is chosen on expected vs received, so this column is not the amount the carrier owes; do not total it or call it a debt. Say how many more there are.
- Table 3 (if step 3 ran): per status - statements, goods lines, amount. Point out the "awaiting payment" row; advise checking the Statements screen for duplicates before paying.
- Relay the COD `note` in plain words: only delivered or lost COD parcels count; parcels Boxme marks as reconciled carry no separate amount, so their received equals the COD.
- Next: chase the carrier with the abnormal tracking codes (Finance > COD reconciliation in Omisell); `/omisell:track-shipment` for one parcel; `/omisell:marketplace-settlement` for marketplace payouts.

## Do not

- Do not call the statement amounts "shipping fees" or "carrier charges": the tool reports them as cost of goods including VAT.
- Do not print carrier ids or warehouse ids; use tracking codes and names.
- Do not mark anything as reconciled or paid from Claude; that is done on the Omisell screen.

## Omisell house rules (apply to every step of this skill)

Never mix data across businesses. A result `business_required` means you forgot it: ask, do not guess.

**Permissions.** Some calls are refused for this user. Translate, never print the raw error:

- a timeout → say that part took too long, offer a narrower period or fewer items, and keep the parts that worked.
Run what you can; one refused tool never ends the whole answer.

**Writes: preview, confirm, check.** Write tools only PROPOSE: they return a preview, a `request_id` and a one-time `confirm_token`. Show the preview (what changes, how many items, anything blocked). Call `confirm_action` only when the user clearly says yes to THAT preview in their latest message. Then call `get_action_status` and report succeeded / failed items. Prefer a `dry_run_*` tool first when one exists; when none does, the write tool's own proposal is the preview. If `confirm_action` answers `token_expired` or `invalid_or_used_token`, propose again and show the new preview; `already_handled` means read `get_action_status`; `batch_too_large` means split into batches of at most 200; `write_disabled` means writing is off for this business (say so, point to the Omisell screen); `permission_denied` is the permission refusal above, re-checked at confirm time (if the user is the owner, the connection lacks this write permission: reconnect and tick it); `not_found` means the request is gone: propose again; `audit_unavailable` means nothing was changed: say it did not start and offer to propose again later; `dispatch_failed` means it most likely did not start: ask the user to check the Omisell screen before proposing again, so the change is never applied twice. A status reply where you expected a preview means the same change was already proposed or done: report that status, do not confirm.

**Time and money.** Tools speak unix seconds. Show dates in the business country's time zone (VN, TH: UTC+7; PH: UTC+8) as dd/mm/yyyy. Money stays in the store's own currency with its symbol. Every number carries its period ("7 days to 05/11/2026"). When the user gives no period, use the skill's default (the last 7 days unless the skill says otherwise) and say so; do not ask first. Respect each tool's longest window (often 31 or 90 days): split or shorten, and say which.

**Language.** Reply in the user's language (Vietnamese, Thai or English), including table headers. **Budget.** At most about 6 tool calls per turn. Prefer one aggregate tool over a loop of per-item calls. If the question needs more, answer the core first and offer the rest.
